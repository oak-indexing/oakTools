AEM Expanded Page Index Bundle

A standalone AEM bundle that extracts content from cq:Page nodes — including referenced Content Fragments — and applies the cq:Searchable mixin with search properties, enabling fulltext and semantic search via the cqSiteSearch Oak Elasticsearch index.

By default (ORIGINAL mode), search properties are written directly to the original /content nodes. An alternative MIRROR mode writes them to a shadow tree at /var/indexing/expanded-pages instead. Either way, a lightweight mirror at /var/indexing/expanded-pages is always maintained for operational tracking (dirty flags, Content Fragment backreferences).

Quickstart

1. Add the Maven repository to all/pom.xml

<repositories>
    <repository>
        <id>oak-indexing</id>
        <url>https://oak-indexing.github.io/maven-repository/</url>
        <snapshots><enabled>true</enabled></snapshots>
        <releases><enabled>true</enabled></releases>
    </repository>
</repositories>

2. Add a version property to the root pom.xml

<expanded.pages.version>1.6.2</expanded.pages.version>

3. Add dependency management to the root pom.xml

<dependency>
    <groupId>com.adobe.aem.indexing</groupId>
    <artifactId>expanded-page-index</artifactId>
    <version>${expanded.pages.version}</version>
</dependency>

4. Embed the bundle in all/pom.xml

In the <embeddeds> block of filevault-package-maven-plugin:

<embedded>
    <groupId>com.adobe.aem.indexing</groupId>
    <artifactId>expanded-page-index</artifactId>
    <target>/apps/your-packages/application/install</target>
</embedded>

In the <dependencies> block:

<dependency>
    <groupId>com.adobe.aem.indexing</groupId>
    <artifactId>expanded-page-index</artifactId>
</dependency>

5. Add OSGi configs to your ui.config module

The bundle embeds its own repoinit and service user mapping via Sling-Initial-Content, but in AEM Cloud Service there is a known ordering risk where the bundle can activate before the JCR Installer feeds those configs to ConfigAdmin. To guarantee reliable startup, add these two files to your project's ui.config module:

ui.config/.../osgiconfig/config/org.apache.sling.jcr.repoinit.RepositoryInitializer~expanded-page-index.cfg.json

{
  "scripts": [
    "create path (sling:Folder) /var/indexing/expanded-pages/content\n\ncreate service user expanded-page-index-service with forced path system/cq:services/expanded-page-index\n\nset principal ACL for expanded-page-index-service\n  allow jcr:read,jcr:modifyProperties,jcr:nodeTypeManagement on /content\n  allow jcr:read on /conf\n  allow jcr:all on /var\n  allow jcr:read on /oak:index\nend"
  ]
}

ui.config/.../osgiconfig/config/org.apache.sling.serviceusermapping.impl.ServiceUserMapperImpl.amended~expanded-page-index.cfg.json

{
  "user.mapping": [
    "com.adobe.aem.indexing.expand:expanded-page-index=[expanded-page-index-service]"
  ]
}

6. Deploy the Oak indexes

The bundle requires two Oak indexes before it activates. These are deployed by Adobe into your AEM Cloud Service environment:

  • cqPageMirror-1-custom-1 — tracks cq:PageMirror nodes (dirty flags, move detection)
  • cqFragmentMirror-1-custom-1 — tracks cq:FragmentMirror nodes (CF backreferences)
The bundle is a strict NOP until these two indexes are present — it is safe to deploy the bundle ahead of time and wait for index deployment. The cqSiteSearch Elasticsearch index is required for search queries to work, but is not a condition for the bundle to activate.

Configuration

The bundle and its scheduler are both configured via a single OSGi PID com.adobe.aem.indexing.expand.service.SearchableIndexServiceImpl ("Expanded Page Index Configuration" in the OSGi Configuration Manager):

PropertyDefaultDescription
cron.expression 0/30 * * * * ? Cron expression controlling how often the scheduler triggers a run
concurrent false Allow a new run to start while a previous one is still executing
searchMode ORIGINAL Where to write cq:Searchable — ORIGINAL (on /content nodes) or MIRROR (on /var/indexing/ nodes). See Search Modes.
referencePropertyPattern fragmentPath Regex (full match) applied to property names on cq:Page subnodes to identify Content Fragment references. Adjust when your components use a non-standard property name (e.g. cfArticleReference, cf.*Reference).
contentPropertiesPropertyName elementNames Name of the sibling property that lists which fragment fields to extract (source-driven / WKND style). Set to empty to disable this strategy.
contentPropertyPattern (empty) Regex (full match) applied to property names inside the fragment's jcr:content/data/master node. All matching properties are extracted as body text (pattern-driven / Telekom style). Leave empty to disable.
applySearchableToFragments false When true, applies the cq:Searchable mixin to Content Fragment nodes directly, making CFs searchable alongside pages. See Fragment Indexing.
extractionStrategy RENDER How page body text is extracted — RENDER (render the page and extract text from the HTML) or PROPERTY_WALK (walk JCR properties via regex). See Page Extraction Strategy.
renderTimeoutMs 5000 RENDER mode only. Per-page render timeout (ms); a page exceeding this is treated as a transient failure and retried on the next scheduled run.
renderBatchSize 50 RENDER mode only. Max dirty pages processed per scheduler tick, since each render is expensive. PROPERTY_WALK processes all dirty pages in a single run.
maxRetryAttempts 5 After this many consecutive extraction failures for a page, stop retrying automatically and mark it failed=true (excluded from the dirty queue) rather than let it block other pages forever. Applies to both extraction strategies.

Page Extraction Strategy

Two strategies control how a page's body text (and Content Fragment references) are extracted. Only one is active at a time, selected via extractionStrategy. RENDER is the default and needs no further configuration; PROPERTY_WALK is for finer-grained control over what gets indexed.

RENDER (default) — renders each page through Sling's own request-processing pipeline (SlingInternalRequest) and extracts text from the resulting HTML's <main> landmark (falling back to <body>). Content Fragment references are discovered automatically during the render (no referencePropertyPattern/contentPropertiesPropertyName/contentPropertyPattern config needed) — a wrapping ResourceResolver records every Content Fragment actually resolved while rendering the page and its nested includes/components. Use this when components don't expose extractable properties, or when the rendered output (not raw property values) best represents what should be searchable.

Notes on RENDER mode:

  • Experience Fragment container pages (which redirect to /master on a direct render) are skipped rather than rendered.
  • Each render runs on its own timeout-bounded worker thread with its own dedicated ResourceResolver, so a hung render never blocks or races other pages.
  • The mirror node's extractedVia property records which strategy (PROPERTY_WALK or RENDER) produced each page's content.
  • renderBatchSize and renderTimeoutMs only apply to this mode.

PROPERTY_WALK — walks the page's JCR properties and extracts text via the Content Fragment extraction strategies below (referencePropertyPattern, contentPropertiesPropertyName, contentPropertyPattern). Cheap and fast; requires components to expose text-bearing properties that the configured patterns can find. Enable it explicitly: 

{
  "extractionStrategy": "PROPERTY_WALK"
}

Content Fragment extraction strategies

(Used by PROPERTY_WALK mode only — RENDER mode discovers Content Fragment references automatically, see above.)

Two strategies control how text is pulled out of referenced Content Fragments. They run independently and can be used simultaneously.

  • Source-driven (WKND style) — the component node carries a property (default elementNames) that explicitly lists which fragment fields to include. Use this when your components already declare which fields they render.
  • Pattern-driven (Telekom style) — a regex (contentPropertyPattern) is matched against all property names inside the fragment's data/master node; every matching property is extracted. Use this when components do not declare field names, or to extract fields from many different CF models uniformly.
Note on contentPropertyPattern: this same regex is also used by standalone fragment indexing (applySearchableToFragments) to decide what a CF's own search document contains. Both uses answer the same question ("what is this fragment's searchable substance?") for two different destinations: here, the answer becomes content added to a referencing page; there, it becomes the fragment's own cq:searchContent. In practice a given deployment picks one of these two cases (embed content in pages, or index fragments as standalone documents), so one shared pattern is sufficient.

Example config using both strategies together:

{
  "searchMode": "ORIGINAL",
  "extractionStrategy": "PROPERTY_WALK",
  "referencePropertyPattern": "cf.*Reference",
  "contentPropertiesPropertyName": "elementNames",
  "contentPropertyPattern": "body|text|description"
}

What It Does

The bundle extracts content from cq:Page nodes (including referenced Content Fragments) and applies the cq:Searchable mixin with search properties to the target node (original or mirror, depending on mode). A lightweight mirror at /var/indexing/expanded-pages tracks operational state regardless of mode.

  • Real-time updates — JCR observation tracks page and Content Fragment changes automatically; runs only on the cluster leader to prevent concurrent write conflicts on publish
  • Content Fragment support — dereferences and includes CF content in the extracted body
  • Move handling — efficiently updates paths when pages are moved
  • Incremental processing — only processes pages changed since the last run
  • HTML stripping — indexes clean text, not markup
  • Semantic search ready — compatible with Oak inference configs for vector embeddings

Content Fragment backreferences

When a Content Fragment is updated, all pages referencing it are automatically re-indexed:

  1. Pages record which CFs they use (fragmentReferences property on the mirror node)
  2. CF mirrors record which pages reference them (referencedBy property)
  3. A CF update marks all referencing page mirrors dirty, triggering re-extraction on the next scheduled run

This works both through real-time JCR observation and a periodic catch-up scan over all CFs (the safety net for anything the observation listener misses, e.g. a restart window) — the catch-up scan runs regardless of applySearchableToFragments, so it applies even if you only embed CF content in pages and never index fragments as standalone documents.

Search Modes

ORIGINAL (default)

cq:Searchable mixin and search properties are written to the original /content nodes. The Elasticsearch index covers /content directly.

Search query:

SELECT [cq:searchTitle], [cq:searchDescription], [jcr:path]
FROM [cq:Searchable]
WHERE ISDESCENDANTNODE('/content/mysite/us/en')
AND contains(*, 'search terms')
OPTION (INDEX TAG cqSiteSearch)

MIRROR

cq:Searchable mixin and search properties are written to mirror nodes at /var/indexing/expanded-pages. The Elasticsearch index covers /var/indexing/expanded-pages.

Search query:

SELECT [cq:searchTitle], [cq:searchDescription], [path]
FROM [cq:Searchable]
WHERE ISDESCENDANTNODE('/var/indexing/expanded-pages/content/mysite/us/en')
AND contains(*, 'search terms')
OPTION (INDEX TAG cqSiteSearch)

To switch to MIRROR mode, add an OSGi config to your ui.config:

ui.config/.../osgiconfig/config/com.adobe.aem.indexing.expand.service.SearchableIndexServiceImpl.cfg.json

{
  "searchMode": "MIRROR"
}

Fragment Indexing

By default only cq:Page nodes receive the cq:Searchable mixin. Set applySearchableToFragments: true to also index Content Fragments directly, so CF-only searches return fragments as first-class results alongside pages.

Enable via OSGi config:

{
  "applySearchableToFragments": true
}

What changes when enabled:

  • Phase 0 applies cq:Searchable to CF nodes in addition to propagating dirty flags to referencing pages
  • The periodic catch-up scan over all CFs under /content/dam (not only those referenced by a page) always runs, regardless of this flag — it's what catches a CF edit missed by the observation listener (e.g. a restart window) and propagates it to any referencing page. This flag only controls whether the scan's discovered CFs also get cq:Searchable applied directly to themselves.
  • Stale CF mirrors whose original /content/dam node has been deleted are cleaned up on the next run

Where the mixin lands depends on searchMode:

ModeCF target
ORIGINAL (default)Original CF node at /content/dam/.../my-fragment
MIRRORCF mirror node at /var/indexing/expanded-pages/content/dam/.../my-fragment

Fragment body text is extracted using contentPropertyPattern only — the source-driven (elementNames) strategy requires a component context and is not available for standalone CFs. Configure a pattern to extract body content: 

{
  "applySearchableToFragments": true,
  "contentPropertyPattern": "body|text|description"
}

Searching pages and fragments (ORIGINAL mode):

SELECT * FROM [cq:Searchable]
WHERE ISDESCENDANTNODE('/content')
AND contains(*, 'search terms')
OPTION (INDEX TAG cqSiteSearch)

Searching pages and fragments (MIRROR mode):

SELECT * FROM [cq:Searchable]
WHERE ISDESCENDANTNODE('/var/indexing/expanded-pages/content')
AND contains(*, 'search terms')
OPTION (INDEX TAG cqSiteSearch)

Choosing a configuration for your use case

The options above combine differently depending on what you're trying to achieve. Three common scenarios:

"I have pages and fragments, and I want both searchable — including fragments nobody references"

Set applySearchableToFragments: true. Fragment discovery scans all CFs under /content/dam, not just ones referenced by a page, so un-referenced fragments are covered too. Pick a contentPropertyPattern that matches the fields that make up a fragment's own searchable content (see the note on this pattern's dual role above).

"I want to control exactly what content fragment fields end up in a page's cq:searchContent — and avoid pulling in generic/shared fragment content"

Set extractionStrategy to PROPERTY_WALK and use contentPropertiesPropertyName (source-driven / WKND style) rather than contentPropertyPattern. contentPropertiesPropertyName requires each component to explicitly declare the fragment fields it renders — the most precise option, since it can't accidentally pick up a field just because its name matches a broad regex. contentPropertyPattern is coarser (any field matching the pattern is pulled in, across every CF model), which is easier to set up but easier to over-match generic/shared fields with. Avoid RENDER mode for this goal — it extracts whatever text is inside <main> on the rendered page, with no per-field control at all.

"I just want my pages searchable, including whatever text comes from the fragments they use — I don't need fragments searchable on their own"

Leave applySearchableToFragments at its default (false). Either extraction strategy works, but they differ in setup cost:

  • RENDER (default) needs no Content Fragment configuration at all — CF references and their rendered text are discovered automatically from the page's actual rendered output.
  • PROPERTY_WALK requires you to configure referencePropertyPattern (to find the CF reference property on your components) and at least one of contentPropertiesPropertyName / contentPropertyPattern (to decide what to pull from the fragment) — with nothing configured, referenced fragment content is silently skipped.

So RENDER is the zero-config path for this use case; PROPERTY_WALK gives you more control (see the previous scenario) at the cost of having to configure it correctly for your components and CF models.

Search Properties

Both modes expose the same properties on the cq:Searchable node:

PropertyDescription
cq:searchTitlePage title
cq:searchDescriptionPage description
cq:searchContentExtracted page body (multi-value, HTML stripped)

In ORIGINAL mode these sit on the /content/... page node. In MIRROR mode they sit on the corresponding /var/indexing/expanded-pages/... mirror node.

Mirror structure (operational tracking)

The mirror at /var/indexing/expanded-pages is always maintained regardless of mode. It holds operational state only — no search properties in ORIGINAL mode. 

/var/indexing/expanded-pages/
├── state/
│   └── lastRun              (timestamp of last successful extraction run)
└── content/                 (mirrors /content)
    └── mysite/
        └── us/
            └── en/
                └── page/    (cq:PageMirror)
                    ├── path                 = "/content/mysite/us/en/page"
                    ├── dirty                = false
                    ├── fragmentReferences   = ["/content/dam/fragments/..."]
                    ├── extractedVia         = "RENDER" | "PROPERTY_WALK"
                    ├── retryCount           = 0      (consecutive extraction failures)
                    └── failed               = false  (true once retryCount reaches maxRetryAttempts)

Troubleshooting

Bundle does not start — extractionService unsatisfied

The ExpandedPageIndexScheduler depends on ExpandedPageIndexService. If the service component is unsatisfied, check it directly in the OSGi console and look for any unsatisfied references there.

Bundle starts but logs "Cannot derive user name"

The service user mapping was not processed before the bundle activated. Add the ServiceUserMapperImpl.amended config to your ui.config module as described in Quickstart step 5.

Bundle starts but mirror is empty

Cause: Oak indexes not yet deployed.
Check: Browse to /oak:index/cqPageMirror-1-custom-1 in CRXDE. If missing, the indexes have not been deployed yet. The bundle logs "Oak indexes not yet available" each scheduler cycle until they exist.

Bundle starts, indexes exist, but extraction never runs

Look for "Content extraction service activated" in error.log. If absent, the service user expanded-page-index-service may not have been created by the bundle's repoinit script. Check for repoinit errors at startup.

Elasticsearch index is empty

  1. Confirm the cq:Searchable mixin is present on target nodes (CRXDE — check a /content page in ORIGINAL mode, or a /var/indexing/expanded-pages mirror node in MIRROR mode)
  2. Confirm the elastic-async lane is running — check IndexStats for elastic-async in the JMX console
  3. Confirm a cqSiteSearch index exists under /oak:index and has type=elasticsearch

Searches return no results

  1. Confirm the Elasticsearch index contains documents (check via the Oak Query Diagnostics or ES API)
  2. Confirm the search path in your query matches the mode — /content/... for ORIGINAL, /var/indexing/expanded-pages/... for MIRROR
  3. Confirm OPTION (INDEX TAG cqSiteSearch) is present in your query

Pages not updating after content changes

  • Check lastRun timestamp at /var/indexing/expanded-pages/state — it should update every 30 seconds
  • Check error.log for "Previous extraction still running" — a run is taking longer than the scheduler interval

RENDER mode: pages stuck retrying / never indexed

  • Check error.log for "Render timed out after <N>ms" — increase renderTimeoutMs if pages are legitimately slow to render, or investigate why the render is hanging.
  • Check for "Render returned status <code>" — a non-200, non-redirect response (e.g. a component throwing) fails the render; fix the underlying rendering error.
  • A 3xx response is treated as retry-able, not a hard failure — Experience Fragment container pages are the one case that's expected and pre-filtered (never attempted). Other redirects usually indicate a page that isn't safely renderable standalone.
  • After maxRetryAttempts consecutive failures, the page mirror is marked failed=true and excluded from the dirty queue. Use the FailedPageCount attribute and listFailedPages() JMX operation to find them, and retryFailedPages(pathPrefix) to re-queue them once the cause is fixed.
